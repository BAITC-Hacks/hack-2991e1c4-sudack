# Career Quest by Sudack

AI-навигатор карьеры для сотрудников и HR, созданный командой Sudack на хакатоне HackAlem AI (трек Halyk Bank, кейс «Career Quest»). Сотрудник открывает свой профиль и видит, где он относительно следующего грейда, получает одну-три рекомендованные активности развития с объяснением на нескольких факторах, отмечает активность выполненной и видит, как сдвинулся прогресс. HR видит, какие навыки проседают по компании, у кого нет полезного следующего шага, кто выпадает из развития и что изменит новое событие ещё до его создания.

Ядро решения — качество и объяснимость рекомендации, а не интерфейс. Каждая рекомендация строится детерминированным, проверяемым скорингом; LLM только выбирает среди лучших кандидатов и пишет объяснение, и всё написанное проверяется по фактам до показа. Если LLM недоступна или её текст не опирается на факты, те же факты выводятся шаблоном и помечаются как шаблон.

## Архитектура

```
 Браузер ──> Фронт (Next.js, :3000) ──> Go API (Echo + SQLite, :8080) ──> AI-сервис (FastAPI, :8001) ──> OpenAI / NVIDIA (опционально)
                                             │                                  │
                                    хранит кит и импорт,             stateless: считает, объясняет,
                                    права сотрудник/HR,              моделирует, оценивает эффект
                                    транзакции прогресса
```

| Сервис | Каталог | Ответственность | Документация |
| --- | --- | --- | --- |
| Фронт | `frontend/` | Вход по роли, экран сотрудника (профиль, траектория, рекомендации с блоком «как рассчитано», «почему не X», маршрут до грейда, кнопка «выполнено»), экран HR (проседающие навыки, список «без шага», участие, риск выпадения, конструктор события, импорт) | `frontend/README.md`, `frontend/FRONTEND.md` |
| Go API | `backend/` | Импорт кита при первом старте и загрузка дополнительных профилей HR-ом, ролевые токены с демо-логином, права сотрудник/HR, проверки допустимости событий, идемпотентные транзакции прогресса, HR-агрегаты. Вызывает AI-сервис с полным контекстом одного сотрудника | `backend/BACKEND.md`, `backend/README.md` |
| AI-сервис | `sudack-ai/` | Детерминированный скоринг, выбор и объяснение через LLM с валидацией, шаблонный фолбэк, симулятор маршрута до грейда, риск выпадения, эффект черновика события | `sudack-ai/README.md`, `sudack-ai/docs/api.md`, `sudack-ai/docs/AI_SERVICE.md` |

AI-сервис не хранит данных и не знает про права: Go в каждом запросе присылает сотрудника, профиль целевого грейда, каталог событий и историю этого сотрудника. Имена в модель не передаются.

## Запуск одной командой

Нужен Docker с Compose v2.

```bash
cp .env.example .env          # опционально: добавьте OPENAI_API_KEY для объяснений от LLM
docker compose up --build
```

| URL | Что |
| --- | --- |
| http://localhost:3000 | Фронт |
| http://localhost:8080/healthz | Проверка Go API |
| http://localhost:8080/api/v1/auth/demo-token | Демо-логин (POST role + employee_id) |
| http://localhost:8001/docs | OpenAPI AI-сервиса |

Без ключа система работает целиком: объяснения приходят из многоязычного шаблона и помечены `template`. С ключом `LLM_MODEL` по умолчанию `gpt-4o`, которая прошла наши живые проверки на русском, казахском и английском.

**Взаимозаменяемые LLM-провайдеры.** AI-сервис говорит с любым провайдером по протоколу OpenAI chat-completions, поэтому провайдер — это базовый URL, ключ и имя модели. `LLM_PROVIDERS` (по умолчанию `openai,nvidia`) задаёт порядок отказоустойчивости; `GET /providers` на AI-сервисе показывает активную цепочку; каждая рекомендация называет ответивший движок в `llm_provider` и `llm_model`. Цепочка работает в одном дедлайне (`LLM_TIMEOUT`): быстро упавший провайдер отдаёт оставшееся время следующему, и никакой провайдер, кроме последнего, не может занять больше 75% остатка. Проверено живьём: при `LLM_PROVIDERS=nvidia,openai` вызов NVIDIA падает, OpenAI отвечает, ответ содержит `llm_provider: openai`. Хакатонный ключ NVIDIA сейчас отдаёт список моделей, но возвращает 401 на inference, поэтому NVIDIA работает как настроенный резерв до активации ключа; подробности в `sudack-ai/docs/VERDICT_AUDIT.md`.

`FRONTEND_USE_MOCKS` в `.env` определяет, ходит ли фронт в Go API (`false`, по умолчанию) или работает на встроенном синтетическом датасете (`true`, запасной демо-режим). В режиме встроенных данных браузер напрямую вызывает AI-сервис по адресу `FRONTEND_AI_URL` за живыми объяснениями LLM, блоком «почему не X», маршрутом до грейда, риском выпадения и конструктором события, так что AI-слой показывается без Go API; если AI-сервис недоступен, экраны откатываются к локальному расчёту и сообщают об этом. Имена сотрудников в этом режиме не покидают браузер. **Прямой путь браузер → AI — только запасной демо-режим:** рабочая схема — фронт → Go API → AI-сервис, где Go владеет данными, правами и вызовом AI, и именно её поднимает `docker compose up` по умолчанию. Для реального сценария держите `FRONTEND_USE_MOCKS=false`; запасной режим нужен, чтобы показать AI-слой, если Go API недоступен.

### Запуск сервисов по отдельности

```bash
# AI-сервис

# Go API

```

## Сценарий демо

1. **Войдите.** Экран входа получает ролевой токен от Go API: «Я сотрудник» с выбором сотрудника или «Я HR». Стартовый кит импортируется в SQLite при первом старте. Как HR нажмите **Импорт данных**, чтобы загрузить дополнительные `employees.json` и `activity_history.csv` в том же формате — так загружаются проверочные профили жюри; готовые ловушечные профили с ожидаемыми ответами лежат в `docs/jury-profiles/`, загруженные сотрудники сразу появляются в поиске на входе.
2. **Откройте сотрудника** (например, `E0028`). В профиле роль, грейд, стаж, навыки против требований следующего грейда, готовность, пройденные и пропущенные активности.
3. **Прочитайте рекомендации.** Одна-три активности, у каждой причина на языке сотрудника и раскрывающийся блок «как рассчитано»: требование следующего грейда, разрыв по навыку с точными уровнями, история участия по этим навыкам, реальный прирост от активности и формула оценки. Блок «почему не X» объясняет, почему навык с самым большим разрывом не стоит первым, когда история или критичность говорят иначе.
4. **Отметьте активность выполненной.** Уровни навыков растут на `gain` события до его `max_level`, готовность и список рекомендаций обновляются, завершение записывается один раз (идемпотентно).
5. **Откройте маршрут.** Симулятор раскладывает активности до следующего грейда с датами ближайших сессий и суммой часов и перечисляет навыки, которые текущий каталог поднять не может, и почему.
6. **Переключитесь на HR.** Самые частые проседающие навыки, сотрудники без полезного шага, участие по активностям, риск выпадения с причинами и конструктор события, который предсказывает, сколько людей сдвинет новое событие и по какой цене за уровень навыка.

## Как строится рекомендация

Для каждого допустимого события (подходящие роль и грейд, выполненные предусловия, не обязательное, не пройденное, если не повторяемое, не в процессе, есть будущая сессия) AI-сервис считает:

- **Эффективный прирост** по навыку по правилу датасета: `min(current + gain, max_level) - current`.
- **Взвешенное закрытие разрыва**: прирост, ограниченный разрывом до следующего грейда, с весом 2.5 для критичных навыков грейда, 1.5 для остальных требуемых, 0.3 для роста вне требований.
- **Вовлечённость**: сглаженная по Лапласу доля завершений в истории сотрудника по тем же навыкам; события того же типа по другим навыкам с весом 0.3, записи старше года с весом 0.6. Без истории — 0.5.
- **Оценка** `= gap_closed × engagement^0.7`, затем лёгкий штраф, чтобы два соседних шага не целились в один навык.

Лучшие закрывающие разрыв кандидаты уходят в LLM как чистые факты (названия и уровни навыков, флаги критичности и разрыва, описание события, счётчики истории) без весов. Каждая возвращённая причина должна быть на запрошенном языке, упоминать историю и содержать точные текущий, требуемый и итоговый уровни; иначе для этого события берётся шаблонное объяснение, и элемент помечается соответственно. Завершения, записанные после `last_review_date` сотрудника, применяются к его навыкам до скоринга, поэтому прогресс виден до следующей формальной аттестации.

Полные формулы, разобранные примеры и журнал живых проверок — в `sudack-ai/README.md`, `sudack-ai/docs/api.md` и `sudack-ai/docs/VERDICT_AUDIT.md`.

## Сверх обязательного

- **Почему не X.** Контрфактическое объяснение для навыка, который выбрало бы наивное правило.
- **Маршрут до грейда.** План с датами до следующего грейда, часы, путь готовности и дыры каталога с классификацией: нет события, не та аудитория, потолок уровня, предусловия, уже пройдено, нет сессии. На стартовом ките ни один сотрудник не достигает следующего грейда полностью с каталогом из 40 событий, и маршрут точно говорит, каких событий не хватает.
- **Риск выпадения.** Балл на сотрудника из доли пропусков, недавних пропусков, неактивности и зависших активностей, с подсказкой формата, если сотрудник завершает один формат и пропускает другой.
- **Эффект черновика события.** Для события, которое HR собирается создать: кто может участвовать, кто закроет разрыв, прогноз завершений, часы на закрытый уровень навыка, место среди существующего каталога.

## Ограничения из ТЗ

- Рекомендация никогда не опирается на одно поле: каждое объяснение несёт требование грейда, разрыв, историю и прирост, и расчёт показан.
- Нет публичных рейтингов результативности, нет очков за обязательные процессы (обязательные события исключены из рекомендаций), нет реальных персональных данных (датасет синтетический).
- Данные о вовлечённости видны только сотруднику и HR; доступ разделён по ролям в Go API.
- Тон добровольный: пропуски называются без упрёка, и ни один шаг не подаётся как назначение.

## Проверка

```bash
cd sudack-ai && uv run pytest         # 70 тестов: ловушечные профили, контракт, прогон датасета на 200 сотрудников, валидация LLM
cd backend && go test ./...           # 5 интеграционных тестов на стартовом ките с фейковым AI
cd frontend && npm run lint && npm run build
```

Без локального Go тесты бэкенда запускаются в контейнере из корня репозитория:

```bash
docker run --rm -v "$PWD:/work" -w /work/backend golang:1.26.1-bookworm go test ./...
```

Сквозной сценарий через Go API (демо-логин, профиль, рекомендации, маршрут, HR-срез, импорт профилей жюри, идемпотентное завершение, проверки прав) проверен на `docker compose up` 23.09.2026; с `OPENAI_API_KEY` в `.env` рекомендации приходят с `source: llm` за 3–5 с.

Кого удобно открыть на демо: `E0028` (Middle Backend, объяснения на казахском), `E0002` (Middle Backend, русский, маршрут из пяти шагов), `E0008` (Senior Frontend, английский), `E0025` (Junior Data Analyst, казахский) и ловушечные `E0901`–`E0903` после импорта. Сам интерфейс на русском; язык объяснений берётся из `preferred_language` сотрудника.

Живая проверка LLM-слоя одним вызовом для любого сотрудника кита: `cd sudack-ai && uv run python scripts/audit_verdict.py --live E0002`.
